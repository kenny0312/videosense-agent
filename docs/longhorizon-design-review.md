## 四、接口接入(serving 侧四发现,均双关核实)

**结论:gate 实验不受阻(本地 harness 不经 Cloud Run);生产放量前有四件 serving 前置件。**

1. **【关键】--timeout 300 vs 墙钟 900s 直接冲突**:生产部署是 `--timeout 300`(DEPLOY.md:74),超 5 分钟的树被 LB 掐断,**钱烧完、交付为零**。P0 七件无一涉及。→ 前置件:生产开 USE_DEPTH2 前 `--timeout ≥ 1.5×MAX_TREE_WALL_S` 并写进 DEPLOY.md;代码侧墙钟 > 0.8×部署超时即告警/钳位。
2. **【关键】断连孤儿树照烧钱,前端 Stop 是假的**:SSE 线程与响应流零耦合,`abortCtrl.abort()` 只断浏览器侧;断连后请求在 Cloud Run 眼里已完成 → CPU 节流区慢烧,且成本记账在 work() 收尾,**孤儿树可能永远记不上账**。→ 最小修:每请求一个 threading.Event,SSE 生成器探测断连即 set;run_loop 每步/run_fanout 每波查一次,命中走墙钟闸同款软收口(就已有证据收口+记账落盘);同时改 index.html 的"省 token"文案。
3. **【重要】树运行期 SSE 全程静默**:on_step 在整个 spawn_agents 返回后才发一次事件,gen() 无心跳——**15 分钟白屏的下场就是用户按 Stop→触发②→排队双烧**。→ 两行修:`q.get(timeout=20)` 超时 yield SSE 注释行心跳;进阶:子 agent 完成时发"子任务 2/6 完成"粗粒度进度。
4. **【重要】会话锁被整棵树持有 15 分钟** + "工具变任务"的触发条件(">15min 任务出现")太晚:应改成可观测指标(树 P90 墙钟 > 0.5×部署超时 / 断连孤儿成本 > $X/周),建立在每天都在落的 audit 数据上。会话锁问题在②落地后自动降级为秒级,不单独立案。

**推荐接入路径**(与稿子 §4 基本一致,顺序上加一条):spawn_agents **原地升级**(不加新工具位,四步注册免走)→ 五开关默认关 → Phase 1 走本地 harness 出 gate 裁决 → **裁决通过后、生产放量前,先交付上面四件 serving 前置件** → 再翻开关。
