## 三重限定(必须一起读)

### 限定一:**深度 2 的机制一次都没被触发**

89 次跑(含试跑),`spawn_agents` **调用次数 = 0**。B/C 臂的工具表里它一直可见
(已单独验证),是主脑自己选择不用。

所以准确表述是:

> **在当前任务分布 + flash orchestrator 条件下,主脑不选择拆分,深度 2 无从生效。**

**不是**"拆了但没用"。任务分布迁移(1h+ 长视频、真正的库级重活)时必须重开。

### 限定二:**B 与 C 是行为相同的配置,它们的分差就是噪声地板**

`USE_DEPTH2` 全库只在 `pipeline/subagents.py` 内被读取 —— 即**只有真的调用
spawn_agents 时才起作用**。拆分率 0% ⇒ **B ≡ C**。

于是 B、C 的分差是纯测量噪声,而它是:

| 量 | 值 |
|---|---|
| |C−B| 平均 | **0.093** |
| |C−B| 最大 | 0.304 |
| 同题同臂两次跑的分差(纯随机) | 平均 0.057、最大 0.411 |
| **裁决门槛** | **+0.10** |

> **噪声地板(0.093)与判定门槛(0.10)同量级。**
> 即便深度 2 真有 +0.10 的收益,本实验规模(6 题/档 × n=2)也【测不出来】。

任务书自己声明过功效不足("9 对 T2 配对 Wilcoxon 只能检出 ≥约 +0.14"),而 holdout
只有 6 对,更弱。**这条限定让"不建"成为一个决策而非科学结论**:没有证据支持它值钱,
且它确实更贵更慢 —— 按这个证据不投入是对的,但不能宣称"已证明无用"。

### 限定三:**A < B < C 的单调排序不可归因于架构**

两档上都出现 A < B < C(T1:0.198/0.280/0.367;T2:0.358/0.392/0.400),看起来很像
"层数越多越好"。但既然 B ≡ C,这个排序里至少有一段是噪声。A 与 B 的差(0.082)
**小于** B 与 C 的噪声(0.093)—— 所以**"多一个 spawn 工具描述就能提升质量"的假设
不成立**,它落在噪声里。

## 副产品:比裁决本身更有价值的四件事

### 1. 历史成本数字系统性低报 **2.6 倍**

同一批题、同样的行为(LLM 调用 146 vs 147 次、token 1.17×),旧账本 $0.55、新账本 $1.66。
决定性证据:有道题 token **更少**反而更贵。原因是旧账本不计思考 token(按输出价 $9/M)。
→ 项目里所有历史成本数字、以及 memory 里"一次视频分析 ≈ $0.018"这类结论,都要按新账本重算。

### 2. "跑道盲区":12% 的跑次**零交付**

11/89 次撞 16 步墙,钱花了什么都没交出来(最贵一次 $0.239 看了 13 个视频、交付 0 条)。
根因:拆不拆、能不能做完的判断发生在**第 1 步**,那时还不知道有多少活。
已加"跑道将尽"提醒(剩 4 步时告知"要么并行拆、要么就现有证据收口标【未核查】"),
A/B 对照实测把同一题从"0 字"变成"4669 字",花费几乎不变。**但只是部分有效** ——
主跑里 A 臂仍有 2 次撞墙。

### 3. 并行度实测**中位 0.62 个 analyze/步**

`MAX_ANALYZE_PARALLEL` 允许 3,但主脑基本一个一个看。这否定了我一度提出的
"主循环自带并行所以不需要子 agent"的解释 —— 真相更简单:**它就是串行看到撞墙**。

### 4. 五个会让实验"看起来有结果、其实全假"的缺陷(全部已修)

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 判分口径与产品规则冲突(要 video_ids,而 VS 按规则把 id 洗成"第 N 个") | **每一臂恒 0 分**,量的是"洗得干不干净" |
| 2 | T2 防 SQL 捷径从没实现(标了 ts_mask 但无代码执行) | 大脑查库抄时间戳,**一个视频不看**也能答 |
| 3 | analyze 缓存键不含命名空间 | 三臂共享暖缓存,"全口径成本"是假的 |
| 4 | 熔断在飞预留按 pro 档一刀切估价 | 实花 $0.13 顶掉 $0.80 的闸,且**专罚看视频多的臂** |
| 5 | 跑机 surfaced 取"碰过的一切" | gold=3 的题抓到 37 条,precision 崩 |

其中 #4 最阴险:它会系统性偏袒"偷懒"的臂,让报告得出"多 agent 更差"的**反向错误结论**。

## 下一步建议(按价值排序)

1. **修"拆分决策的时机"** —— 现在是开局盲猜,应改成"拿到候选清单后再判一次"。
   可观测触发信号(trace 里现成):①撞墙率 ②`已知待办量 > 剩余步数余量` ③并行度长期偏低却活很多。
   第 ② 条在第 3 步就可判,而拆分决定正好该在那时做。**这比深度 2 值钱 —— 深度 2 解决的是
   "拆了之后怎么组织",而现在卡住的是"根本没拆"。**
2. **若要重跑 gate,先把功效补足**:题数 ×2 或 n=4,否则噪声吃掉效应。
3. **后台任务的触发从未被测过**(gate 实验里 `USE_TASKS=0`)—— 那是独立的一条,值得单测。
4. 深度 2 的代码保留、开关默认关,等任务分布迁移后按第 1 条的触发信号重新立案。
