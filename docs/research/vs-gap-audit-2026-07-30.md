# 给委托人的差距清单:他们做了、VS 没有的

---

## 1. 【一句话总览】

VS 缺的不是能力,是**「让大脑知道自己身处何地、花了多少钱、看漏了什么」的那层元信息**——库里有多少存量、这次查的范围有多大、这一步要花多少钱、我刚才是不是绕圈了,这些对手全都主动喂给模型,VS 全靠模型自己猜。(推断,但由 A/B/C 三组共 12 条独立缺口收敛得出)

## 4. 【Top 5 建议动手顺序】

选取标准:**跟剪辑毫无关系的纯 agent 工程**(可移植性最高)+ 修的是现存真伤而非 nice-to-have + 单条 ≤1 天。

### 第 1 步 — 修 max_steps 出口(表 #1)
**为什么排第一**:唯一一条「不做就在持续伤害用户」的。跑满 16 步 → 告诉用户「服务波动,请再发一次」→ 用户照做 → 再烧 16 步,而 ledger/trace 还全丢了。且这是**纯 agent 工程**,任何 loop 型 agent 都会撞上。
**做法**:`loop_driver.py:415` 不回 None,回诚实文案;`orchestrator.py:158-162` 把 `terminated=="max_steps"` 单独分流,不再走 `_RETRY_MSG`;接上现成的 start_background_task 当「继续卡」。
**验收**:构造一个必然跑满 16 步的题 → 用户看到的是「这题比一轮装得下的大,我已经做到 X,要我用后台任务接着做吗」而不是「服务波动」;且该轮 transcript **有**落盘(`record_loop_turn` 走到);单测断言 `terminated=="max_steps"` 时返回文案不含「临时的服务波动」。

### 第 2 步 — 把 analyze 的重试纳入熔断视野(表 #2),顺手做 subagents 缓存换位(表 #13)
**为什么排第二**:钱。`RETRY_LIMIT=2` 意味着一次 analyze 最坏实花是预留 $0.30 的 **3 倍**,而这层重试对 TreeGuard 完全不可见——熔断的账本是错的,后面所有成本实验的地板都跟着错。subagents 那两行换位顺手做,因为它是同一类「不修就带着上线」的问题,且 spawn_agents 正是当前主推方向。
**做法**:`analyze_video_contextual.py:25` RETRY_LIMIT 降 0(失败即回 FAILURE_ANSWER_PREFIX 信封让大脑决策)**或**把 admit/settle 挪进重试循环逐次预留;`subagents.py:120-129` schema 拼接提到 video_ids 之前。
**验收**:注入一个必失败的 generate,断言 guard 记录的花费笔数 == 实际 LLM 调用次数(现在是 1 vs 3);新增 `tests/pipeline/test_prompt_order.py` 断言两处 system 里 `index(schema) < index(volatile)`;`loop_console` 打出 cached_ratio > 0 且随扇出不塌。

### 第 3 步 — library_state 摘要 + 「omitted ≠ empty」宪法条款(表 #3 + #4,捆绑做)
**为什么捆绑**:它们是同一个事故(skydive「说没有」)的两面——一个让大脑**开局知道存量**,一个让它**不知道时别乱下结论**。分开做只堵一半。也是最可移植的一条:任何「agent + 数据库」系统都缺这个。
**做法**:`loop_driver.py:927` 旁加 `library_state_line()`(一条 GROUP BY + 一条各表 COUNT,TTL 进程缓存,fail-open,照抄对手截断纪律「只列前 12 类,其余 M 类合计 K 个」),注入 `:995-1002`(**绝不能进 `:901` 冻结前缀**);`:855-866` 宪法末追加 4 行。
**验收**:造一个 video_facts 里没有、只在专栏表里有的品类,问「库里有没有 X」→ 回答必须是「在 video_facts 里没有匹配的」而非「库里没有」,且**开局第一步**就应该知道该品类的存量;单测断言 library_state 串出现在 `_loop_system` 里且**不在** `_LOOP_SYSTEM` 里(缓存前缀完整性)。

### 第 4 步 — sql_query 硬上限(表 #12)
**为什么**:唯一一个**无界返回**通道,而且它的结果会一路进 ledger → show_table → transcript 持久化。一条手滑的 `SELECT *` 就能拖垮内存和会话记忆。20-30 行,是全表里性价比最高的一条。
**做法**:`node_executor.py:94` NodeResult 前截断,value 改成 `{rows: rows[:CAP], _truncated, _total, _note}`;`loop_driver.py:754` 让 `_note` 单独成格(**别走 cell=80 的预览路径**,参照 `:209-221` `_soft_note` 的教训)。
**验收**:构造 5000 行返回 → ledger 里只有 2000 行,`_note` 完整出现在回喂里(不被腰斩),大脑下一步用 LIMIT/OFFSET 重查而不是傻等;单测两个(截断触发/未触发)。

### 第 5 步 — report_user_friction 自报遥测(表 #7)
**为什么压轴**:前四条都是止血,这条是**造血**。VS 主线是 eval + GEPA,而 GEPA 第一轮的诚实空结论根本原因是「gen0 val 近天花板」——缺高难度失败样本。agent 自报绕圈是**零成本、每轮都有、代码永远看不见**的失败模式信号源,直接喂题库难度评估。而且它跟剪辑毫无关系,是纯 agent 工程里可移植性最高的一条。
**做法**:第 14 个工具,spec 里写死「这是给系统看的,永远不要跟用户提这个工具」+ category 枚举(含 `agent_self_detected`)+ 每轮每 category 限一条的闭包字典;先只落 `trace.py` 的 step,不接外部服务。
**验收**:跑一批已知会绕圈的 eval 题 → trace 里出现 self_detected 记录,且与 repeat_limit/步数耗尽这些**外部信号的重合率 < 50%**(重合率太高说明它只是在复述代码已知的东西,没有新信息);限流生效(同轮同 category 第二次被吞)。

> **明确排在 Top 5 之外的**:第 8/16 条(转写稿整取 + 压缩)价值高但工作量中且要新工具位,建议作为独立的下一批;第 9(c) 那 8 行 evidence_ts 钳制虽然极便宜,但它属于 answer_guard 那套「命中数进 metrics → 长期为 0 则规则退役」闭环,和第 10 条第三刀一起做更省事。

## 5. 【一条反向观察】——VS 有而他们没有的

1. **美元级实时熔断,且是执行前预留而非事后统计**(已核实):`treeguard.py:104-138` 的 admit 做「预估比对 + 在飞预留」,`loop_driver.py:776-781` 按 analyze 的**实际档位**取估价(flash/pro 不同价)。开源 agent 生态里绝大多数只有 token 计数或 maxTurns,**没有一个是以美元为单位的请求内实时预留**;ChatCut 那边最接近的是 credits,但那是给用户看的账单闸,不是给 agent 看的护栏。三粒度(跨请求日顶/请求内实时/单请求配额)互不重叠这件事,连商业 agent 框架都很少做齐。
2. **成本对模型本身可见,而且是元问题才答**(已核实):`runtime_facts_line` 把 token/花费拼进 system,`treeguard.py:190-210` 触闸后 final_note 明说「累计 $X / 上限 $Y / 触闸后额外发生 $Z」。让 agent **知道自己花了多少钱**并据此决定收口时机,在开源世界近乎绝迹——对手是靠人在外面看仪表盘。
3. **semantic_search 是 agent 的一等公民工具,而不是 RAG 前置管道**(已核实):`node_specs.py:146-171` 让大脑自己决定何时从字面查转语义查、何时从全库收窄到视频内;`node_executor.py:681-699` 还把 analyze 的结论**回写进索引**(用它就长它)。主流 RAG 是「检索→塞进 prompt→生成」的固定流水线,把检索当 agent 可调度的决策点、且带自增长闭环的,少见。
4. **真读画面帧,不是读元数据/字幕装作看过**(已核实):`perception/analyze_video_contextual.py` 是完整多模态调用。ChatCut / OpenChatCut / video-use **全部只读转写稿和轨道元数据**——他们的 `view_asset_frames` 自己都标了「NOT for timeline proof」。这是 VS 最硬的结构性差异:对手在字幕层做「理解」,VS 在像素层。
5. **eval 体系:确定性判据进门禁、AI 裁判只做参考分**(已核实):`evals/judge.py:1` 那行注释是整套的宪法。开源 agent 项目里 LLM-as-judge 几乎清一色是**主判**,VS 是反过来的——机械可判的一律机械判(IoU / 计数 / 泄漏正则 / wilson 显著性),裁判只补语义那一层。ChatCut 那条 inspect_color 原则是「给模型一把尺子当参考」,VS 是「尺子说了算,模型靠边」,更硬一档。
6. **提示词规则带出生证与退役条件的治理制度**(已核实):`lessons.py` 每条带 origin(哪个 PR/事故)+ sunset(什么条件下删)+ MAX_LESSONS=15 由测试强制,而且 L01 的退役闭环真的接上了代码命中计数(`id_scrub_hits`)。把 prompt 当**有预算、会过期的资产**来管,而不是只增不减的垃圾场——这个在开源提示词工程里基本看不到(ChatCut 22 个 SKILL.md 就是纯追加式)。
